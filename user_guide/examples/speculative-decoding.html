Speculative Decoding#

TensorRT Edge-LLM supports MTP, EAGLE3, EAGLE-4, DFlash, DFlash2, LiLiCorr, DSpark, JetSpec, and Domino. Each method uses a different draft architecture and checkpoint contract. Use only a base/draft pair listed under Speculative Draft Checkpoints.

The examples below follow the supported ONNX workflow:

  1. Download the named checkpoint or checkpoint pair.

  2. Export the base and draft components on an x86 host.

  3. Build both engines into the same engine directory on the target.

  4. Run llm_inference with the method-specific proposal settings.

The ONNX-less alternative builds both engines in one command. Choose one workflow; do not run both for the same deployment.

Complete Installation first. Run the build and inference commands from the repository root:

export REPO_DIR=/path/to/TensorRT-Edge-LLM
export WORKSPACE_DIR=$HOME/tensorrt-edgellm-workspace
export INPUT_FILE=$REPO_DIR/tests/test_cases/llm_basic.json
mkdir -p "$WORKSPACE_DIR"
cd "$REPO_DIR"

MTP#

Qwen/Qwen3.5-4B contains its MTP draft layer. One export command produces llm/ for the base and mtp_draft/ for the draft.

Export#

export MODEL_ID=Qwen/Qwen3.5-4B
export MODEL_ROOT=$WORKSPACE_DIR/Qwen3.5-4B-mtp
export MODEL_DIR=$MODEL_ROOT/checkpoints/base

hf download "$MODEL_ID" --local-dir "$MODEL_DIR"
trtedge export "$MODEL_DIR" "$MODEL_ROOT/onnx" --mtp

If export and engine build run on different machines, copy $MODEL_ROOT/onnx to the target before continuing.

Build#

./build/bin/llm_build \
  --onnx-dir "$MODEL_ROOT/onnx/llm" \
  --engine-dir "$MODEL_ROOT/engines" \
  --max-batch-size 1 \
  --max-input-len 2048 \
  --max-kv-cache-capacity 4096 \
  --max-spec-verify-tokens 4 \
  --spec-base

./build/bin/llm_build \
  --onnx-dir "$MODEL_ROOT/onnx/mtp_draft" \
  --engine-dir "$MODEL_ROOT/engines" \
  --max-batch-size 1 \
  --max-input-len 2048 \
  --max-kv-cache-capacity 4096 \
  --max-spec-draft-tokens 4 \
  --spec-draft

Run#

./build/bin/llm_inference \
  --engine-dir "$MODEL_ROOT/engines" \
  --input-file "$INPUT_FILE" \
  --output-file "$MODEL_ROOT/output.json" \
  --spec-decode \
  --spec-draft-top-k 1 \
  --spec-draft-step 3 \
  --spec-verify-tokens 4

MTP is linear: --spec-draft-top-k 1 selects one token at each of three draft steps, and the base verifies those tokens plus the current token. For jump-forward with tree drafting (--spec-draft-top-k above 1), build the base with --max-spec-verify-tokens above the runtime --spec-verify-tokens; chain drafting needs no extra verify positions, and both need --max-spec-draft-tokens above --spec-draft-step, as in the build above.

Dense Qwen3 checkpoints with a trained MTP head follow the same commands. The head must live in the base checkpoint directory under the mtp.* prefix with num_nextn_predict_layers: 1 in config.json, as shipped by AngelSlim/Qwen3-8B-MTP for Qwen/Qwen3-8B. trtedge quantize llm quantizes the head together with the base (--lm_head_quantization also applies to the draft’s shared lm_head), and trtedge export --mtp on the quantized checkpoint produces llm/ and mtp_draft/. The checkpoint-direct builder and trtedge serve --speculative-config '{"method":"mtp"}' build the same pair from the checkpoint directory.

Gemma4 uses a matched assistant checkpoint instead of embedded draft layers. For Gemma4 12B, export the matched base and assistant checkpoints together:

export GEMMA_MODEL_ID=google/gemma-4-12B-it
export GEMMA_ASSISTANT_ID=google/gemma-4-12B-it-assistant
export GEMMA_ROOT=$WORKSPACE_DIR/gemma-4-12B-it-mtp

trtedge export \
  "$GEMMA_MODEL_ID" \
  "$GEMMA_ROOT/onnx" \
  --mtp \
  --mtp-draft-dir "$GEMMA_ASSISTANT_ID"

Build and run $GEMMA_ROOT/onnx/llm and $GEMMA_ROOT/onnx/mtp_draft with the same MTP commands above, substituting MODEL_ROOT=$GEMMA_ROOT. Assistant IDs for other Gemma4 sizes are listed in Supported Models. For jump-forward, Gemma4 chain drafting needs neither extra verify positions nor --max-spec-draft-tokens above --spec-draft-step, and jumps with at most 15 draft steps.

EAGLE3#

This example pairs Qwen/Qwen3-1.7B with AngelSlim/Qwen3-1.7B_eagle3. The base export enables EAGLE verification inputs; the draft checkpoint exports as a regular llm/ component.

Export#

export MODEL_ID=Qwen/Qwen3-1.7B
export DRAFT_ID=AngelSlim/Qwen3-1.7B_eagle3
export MODEL_ROOT=$WORKSPACE_DIR/Qwen3-1.7B-eagle3
export MODEL_DIR=$MODEL_ROOT/checkpoints/base
export DRAFT_DIR=$MODEL_ROOT/checkpoints/draft

hf download "$MODEL_ID" --local-dir "$MODEL_DIR"
hf download "$DRAFT_ID" --local-dir "$DRAFT_DIR"
trtedge export "$MODEL_DIR" "$MODEL_ROOT/base-export" --eagle-base
trtedge export "$DRAFT_DIR" "$MODEL_ROOT/draft-export"

Copy both export directories to the target when using separate machines.

Build#

./build/bin/llm_build \
  --onnx-dir "$MODEL_ROOT/base-export/llm" \
  --engine-dir "$MODEL_ROOT/engines" \
  --max-batch-size 1 \
  --max-input-len 1024 \
  --max-kv-cache-capacity 2048 \
  --max-spec-verify-tokens 60 \
  --spec-base

./build/bin/llm_build \
  --onnx-dir "$MODEL_ROOT/draft-export/llm" \
  --engine-dir "$MODEL_ROOT/engines" \
  --max-batch-size 1 \
  --max-input-len 1024 \
  --max-kv-cache-capacity 2048 \
  --max-spec-draft-tokens 60 \
  --spec-draft

Run#

./build/bin/llm_inference \
  --engine-dir "$MODEL_ROOT/engines" \
  --input-file "$INPUT_FILE" \
  --output-file "$MODEL_ROOT/output.json" \
  --spec-decode \
  --spec-draft-top-k 10 \
  --spec-draft-step 6 \
  --spec-verify-tokens 60

EAGLE3 expands a tree: each of six draft steps retains ten candidates, and the base engine verifies up to 60 positions. Quantizing the draft is supported but can reduce its acceptance rate. For jump-forward, build with --max-spec-verify-tokens above the runtime --spec-verify-tokens.

EAGLE-4#

This example pairs RadixArk/Qwen3.8-27B-NVFP4 with EAGLE-Corp/Qwen3.8-27B-EAGLE4. The draft weights have their own license; see EAGLE-4 Draft Models. The NVFP4 base requires an SM100 or newer GPU.

EAGLE-4 drafters use the EAGLE3 mode; there is no separate method name, and exported configurations record spec_decode_type: "eagle3".

The draft engine contains a low-rank candidate head. It projects the draft state to a low rank (128 for this drafter), scores the full vocabulary from that projection, rescores the best num_candidates tokens (128 for this drafter) with its full lm_head, and outputs their token IDs and log-probabilities instead of full-vocabulary logits. The draft needs no d2t.safetensors.

Export#

The draft configuration names the base layers whose hidden states it reads. A Qwen3.5-family base therefore requires --eagle-draft-dir with --eagle-base; the base export records the resolved layers as eagle_hidden_state_layers ([4, 32, 60] for this pair).

export MODEL_ID=RadixArk/Qwen3.8-27B-NVFP4
export DRAFT_ID=EAGLE-Corp/Qwen3.8-27B-EAGLE4

Each of 12 draft steps keeps four candidates, and the base engine verifies the 16 highest-scoring tree nodes, including the root. As with EAGLE3, only greedy requests use speculative decoding; sampled requests are decoded without a draft.

As for EAGLE3, --spec-verify-tokens is at least --spec-draft-step + 1. With a candidate-head draft or a hybrid (Qwen3.5-family) base, the runtime also rejects trees that exceed these limits:

  • --spec-draft-step is at most 15.

  • --spec-draft-step times --spec-draft-top-k is at most 64.

  • --spec-verify-tokens is at most 64 and at most 1 + K + (D - 1) * K * K, where K is --spec-draft-top-k and D is --spec-draft-step.

  • With a candidate head, --spec-draft-top-k is at most the draft’s num_candidates.

Limitations#

  • The ONNX-less builder pairs EAGLE-4 drafts with the Qwen3.5 base above; other bases are not validated. It rejects Qwen3.5 MoE, Muse-Glimmer, Nemotron and Gemma4 bases before it builds an engine. It also rejects EAGLE-4 drafts whose configuration does not name the base layers they read, drafts with an FP8 KV cache, drafts in the speculators eagle3 checkpoint layout, and a candidate-head draft whose lm_head is quantized; build such a draft with --draft-dense-head. DFlash V2#

DFlash V2 is selected automatically from the draft checkpoint architecture and uses the same public dflash mode as DFlash V1. It adds dynamic grouped causal convolution around every draft attention and MLP sublayer, then uses an in-engine Candidate Selector to construct a predecessor-conditioned seven-token path. The runtime verifies this path with greedy matching or lossless rejection sampling. With --spec-draft-top-k greater than 1, the runtime verifies a parent-conditioned DDTree instead; see DFlash2 DDTree.

DFlash2 DDTree#

--spec-draft-top-k K with K greater than 1 turns the DFlash2 proposal into a tree. The draft still runs one forward pass. For every proposal position and every token of the previous position’s selector support, the runtime scores the current support with the selector, using that token as the predecessor. A tree node’s children are therefore scored with the node’s own token, not with the greedy chain. The DDTree builder keeps the K best children of each node and grows the --spec-verify-tokens N most probable prefixes; the target verifies all N nodes in one pass.

Limit

Value

Children per node K

2 to the checkpoint selector_top_k (16 for the listed drafts), and less than N

Verify nodes N

at most the base engine verify profile and 128; at most 64 for hybrid (GDN or Mamba) targets

Accepted tokens per round

at most the checkpoint block size

Sampling

greedy only; sampled requests run on the vanilla decoder

Build the base with a verify profile of at least N. The draft engine is the same as for the chain:

./build/bin/llm_build \
  --onnx-dir "$MODEL_ROOT/base-export/llm" \
  --engine-dir "$MODEL_ROOT/engines" \
  --max-batch-size 8 \
  --max-input-len 4096 \
  --max-kv-cache-capacity 8192 \
  --max-spec-verify-tokens 32 \
  --spec-base

With the checkpoint-direct builder, add --max-spec-verify-tokens 32 to the trtedge build command above. Then select the tree at runtime:

./build/bin/llm_inference \
  --engine-dir "$MODEL_ROOT/engines" \
  --checkpoint-dir "$MODEL_DIR" \
  --draft-checkpoint-dir "$DRAFT_DIR" \
  --input-file "$INPUT_FILE" \
  --output-file "$MODEL_ROOT/output.json" \
  --spec-decode \
  --spec-draft-top-k 4 \
  --spec-verify-tokens 32

A greedy request that sets spec_proposal_sampling to probabilistic fails in tree mode; use --spec-draft-top-k 1 for probabilistic proposals. The tree verifies more target positions per round than the chain, so its verify cost grows with N and the batch size; on hybrid (GDN) targets each verify node also needs recurrent-state scratch. At larger batch sizes a smaller N (for example 16) is usually faster than 32 or more.

The server accepts the same shape in --speculative-config. verify_tokens also sizes the base engine when --max-spec-verify-tokens is not set:

  --cache-dir /data/edgellm-cache \
  --speculative-config \
  '{"method":"dflash","model":"z-lab/Qwen3.8-27B-DFlash2","draft_top_k":4,"verify_tokens":32}'

FP16, NVFP4, and INT4 checkpoints use the same command. Precision is detected from checkpoint quantization metadata. When the draft is distributed only in FP16, create a matched quantized draft with trtedge quantize draft before building the pair.

LiLiCorr#

LiLiCorr is a DFlash V2 draft whose dflash_config sets projector_type: "lilicorr". It keeps the DFlash V2 backbone but replaces the Candidate Selector with a candidate-lattice head inside the draft engine. For each proposal slot, the draft engine keeps the lilicorr_candidate_topk highest-probability tokens and scores every transition from a candidate in one slot to a candidate in the next. The runtime walks these transition scores to build one token chain, then verifies it with greedy matching or lossless rejection sampling, as in DFlash V2. The published draft uses a block size of 8 (seven proposal slots) and eight candidates per slot.

This example pairs nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB with nvidia/NVIDIA-Nemotron-3.5-Bolt-74B-A9B-24GB-LiLiCorr. Build the engines with the ONNX workflow (export, then llm_build) or directly from the checkpoints, as described in Build from checkpoints.

Packed NVFP4 W2 with FP16 activations on Thor#

Native NVFP4 Markov W2 weights automatically use the SM110 W4A16 backend for unbiased greedy DSpark chain and tree drafting. Export preserves the original packed W2 and scales in dspark_w2_nvfp4.safetensors instead of exporting a dense FP16 W2. The engine builder copies this file alongside dspark_heads.safetensors, which contains W1 and any confidence tensors. Packed-only exports require a runtime with native NVFP4 W2 support; older runtimes cannot load them. No runtime environment variable is required. Selection depends on W2’s checkpoint representation, not the draft backbone precision.

The fast path requires Markov rank 512, vocabulary divisible by 128, and the SM110 nvfp4_a16_blackwell_gemm CuTe DSL artifacts. Other configurations use a dense fallback, materialized at initialization from the packed weights. This fallback also supports logit bias and non-greedy requests without allocating weights during graph execution. Existing FP16-only head sidecars retain their default FP16 behavior.

Select the compute backend through llm_inference --dsparkW2Backend=auto|fp16|fp8|w4a16. The default is auto; no W2 environment variable is required at export or inference. C++ callers set SpecDecodeDraftingConfig::dsparkW2Backend before constructing the runtime. The decoder reads this consolidated runtime configuration once during initialization.

Export records w2_format in dspark_heads_info.json; the builder copies this metadata and the sidecars into the engine directory. Runtime validates the declared format against the available tensors. The former runtime overrides EDGELLM_DSPARK_W2_FP8 and EDGELLM_DSPARK_W2_NVFP4 are no longer read. Use --dsparkW2Backend=fp8, fp16, or w4a16 for explicit comparisons. An explicit unsupported W4A16 selection fails instead of silently falling back. On SM121, auto uses FP16; the SM110 W4A16 kernel is not dispatched there. These backend selections apply to supported unbiased greedy requests. Non-greedy and logit-bias requests retain the dense FP16 path. Initialization logs the stored weight format, requested backend, and selected backend.

The kernel dequantizes packed weights and applies their scales in FP16 before tensor-core multiplication with FP16 activations. It accumulates in FP32 and stores an FP16 correction before adding the backbone logits. These rounding and reduction semantics differ from the dense kernel; this is not a bitwise-equivalent mode. Validate model accuracy, acceptance, and end-to-end throughput with the intended chain or tree configuration. Packed weights are repacked and scratch buffers are allocated at initialization, before CUDA graph capture. Retaining the dense fallback weights means this option does not reduce the overall resident W2 allocation. For vocabulary 131072, rank 512, and maximum batch 4, the opaque packed layout and scratch add approximately 37 MiB beyond the dense fallback. The temporary source layout adds another 36 MiB during initialization and is released after repack completes.

JetSpec#

JetSpec is a paired-draft speculative decoding method that uses a dedicated external draft checkpoint and branching tree verification. TensorRT Edge-LLM validates JetSpec with Qwen/Qwen3-8B and the JetSpec/jetspec-qwen3-8b draft checkpoint.

JetSpec shares the cached-draft runtime contract with DFlash, but the draft uses causal proposal attention. Use --jetspec-base for the base export, --jetspec-draft for the draft export, and run with --spec-draft-top-k > 1. --spec-proposal-tokens configures the usable proposal depth independently of the root-inclusive target verification budget.

Set "enable_thinking": false in the input JSON for Qwen3-8B JetSpec validation. This matches the Qwen3 chat-template behavior used by the validated greedy accuracy and throughput runs.

Example#

Example model: Qwen/Qwen3-8B with JetSpec/jetspec-qwen3-8b

Step 1: Export (x86 Host)#

export WORKSPACE_DIR=$HOME/tensorrt-edgellm-workspace
export MODEL_NAME=Qwen3-8B
mkdir -p $WORKSPACE_DIR
cd $WORKSPACE_DIR

# Download JetSpec draft model to workspace
git clone https://huggingface.co/JetSpec/jetspec-qwen3-8b
cd jetspec-qwen3-8b && git lfs pull && cd ..

# Export JetSpec tree base model
trtedge export \
  Qwen/Qwen3-8B \
  $MODEL_NAME/onnx/tree_base_export \
  --jetspec-base \
  --jetspec-draft-dir jetspec-qwen3-8b

# Export JetSpec draft model
trtedge export \
  Qwen/Qwen3-8B \
  $MODEL_NAME/onnx/draft_export \
  --jetspec-draft \
  --jetspec-draft-dir jetspec-qwen3-8b

# Put outputs in the layout used by the build steps below
mkdir -p $MODEL_NAME/onnx/tree_base $MODEL_NAME/onnx/draft
cp -a $MODEL_NAME/onnx/tree_base_export/llm/. $MODEL_NAME/onnx/tree_base/
cp -a $MODEL_NAME/onnx/draft_export/jetspec_draft/. $MODEL_NAME/onnx/draft/

This produces:

  • $WORKSPACE_DIR/$MODEL_NAME/onnx/tree_base/ - JetSpec base model with target hidden-state outputs and tree-attention inputs

  • $WORKSPACE_DIR/$MODEL_NAME/onnx/draft/ - JetSpec draft model

Step 2: Transfer to Device#

scp -r $WORKSPACE_DIR/$MODEL_NAME/onnx \
  <device_user>@<device_ip>:~/tensorrt-edgellm-workspace/$MODEL_NAME/

Step 3: Build Engines (Thor Device)#

export WORKSPACE_DIR=$HOME/tensorrt-edgellm-workspace
export MODEL_NAME=Qwen3-8B
cd /path/to/TensorRT-Edge-LLM

# Build JetSpec base engine
./build/bin/llm_build \
  --onnx-dir $WORKSPACE_DIR/$MODEL_NAME/onnx/tree_base \
  --engine-dir $WORKSPACE_DIR/$MODEL_NAME/engines \
  --max-batch-size 1 \
  --max-input-len 2048 \
  --max-kv-cache-capacity 4096 \
  --max-spec-verify-tokens 128 \
  --spec-base

# Build JetSpec draft engine
./build/bin/llm_build \
  --onnx-dir $WORKSPACE_DIR/$MODEL_NAME/onnx/draft \
  --engine-dir $WORKSPACE_DIR/$MODEL_NAME/engines \
  --max-batch-size 1 \
  --max-input-len 2048 \
  --max-kv-cache-capacity 4096 \
  --max-spec-draft-tokens 16 \
  --spec-draft

Step 4: Run Inference (Thor Device)#

cd /path/to/TensorRT-Edge-LLM

./build/bin/llm_inference \
  --engine-dir $WORKSPACE_DIR/$MODEL_NAME/engines \
  --input-file $WORKSPACE_DIR/input.json \
  --output-file $WORKSPACE_DIR/output_jetspec.json \
  --spec-decode \
  --spec-draft-top-k 7 \
  --spec-proposal-tokens 15 \
  --spec-verify-tokens 128

Key differences from EAGLE3 and DFlash:

  • --jetspec-base exports the base model for JetSpec tree verification

  • --jetspec-draft exports the dedicated JetSpec draft model into jetspec_draft/

  • --spec-draft-top-k 7 matches the validated JetSpec Qwen3-8B tree configuration

  • --spec-verify-tokens 128 is the validated tree verification budget including the root token; 128 is also the largest tree any speculative mode verifies, on every platform

  • --spec-proposal-tokens 15 selects the usable proposal depth from the block-16 draft

  • Qwen3-8B JetSpec validation uses thinking mode disabled

Jump-forward needs a runtime --spec-verify-tokens below the built --max-spec-verify-tokens; with both at 128, as above, the runtime ignores the flag.

Domino#

Domino pairs Qwen/Qwen3-8B with the Huang2020/Qwen3-8B-Domino-b16 draft checkpoint; the Qwen3-4B and Qwen3.6-27B drafts from the same collection follow the identical workflow. The draft transformer, base engine, and verification path are the DFlash block-16 draft; Domino adds a causal correction head. The draft engine emits a shared top-2048 candidate pool with its base logits at every proposal position, the correction codebook rows, and the projected draft hidden states. The runtime runs a per-position GRU rollout over the pool (domino_heads.safetensors, exported next to the draft ONNX), records each position’s corrected pool scores, and builds the verify tree from them with the same DDTree builder DFlash uses: --specDraftTopK 1 is the greedy chain and --specDraftTopK > 1 fans out around it.

Domino checkpoints are plain DFlash checkpoints with dflash_config.projector_type = "domino"; --dflash-draft detects them automatically, and --domino-base / --domino-draft are the explicit spellings. Domino supports greedy decoding only; chain (--specDraftTopK 1) and tree (--specDraftTopK up to 8) run on the same engine pair.

Export#

export MODEL_ID=Qwen/Qwen3-8B
export DRAFT_ID=Huang2020/Qwen3-8B-Domino-b16
export MODEL_ROOT=$WORKSPACE_DIR/Qwen3-8B-domino
export MODEL_DIR=$MODEL_ROOT/checkpoints/base
export DRAFT_DIR=$MODEL_ROOT/checkpoints/draft

hf download "$MODEL_ID" --local-dir "$MODEL_DIR"
hf download "$DRAFT_ID" --local-dir "$DRAFT_DIR"

trtedge export \
  "$MODEL_DIR" "$MODEL_ROOT/base-export" \
  --domino-base --domino-draft-dir "$DRAFT_DIR"

trtedge export \
  "$MODEL_DIR" "$MODEL_ROOT/draft-export" \
  --domino-draft --domino-draft-dir "$DRAFT_DIR"

The base export lands in base-export/llm/. The draft export lands in draft-export/dflash_draft/ together with domino_heads.safetensors, which llm_build copies into the engine directory. The sidecar holds the GRU input projection precomputed over the vocabulary (about 0.9 GB for Qwen3-8B), so the rollout reads one row per token instead of the full GRU input weight.

Build#

./build/bin/llm_build \
  --onnxDir "$MODEL_ROOT/base-export/llm" \
  --engineDir "$MODEL_ROOT/engines" \
  --maxBatchSize 1 \
  --maxInputLen 1024 \
  --maxKVCacheCapacity 2048 \
  --maxSpecVerifyTokens 60 \
  --specBase

./build/bin/llm_build \
  --onnxDir "$MODEL_ROOT/draft-export/dflash_draft" \
  --engineDir "$MODEL_ROOT/engines" \
  --maxBatchSize 1 \
  --maxInputLen 1024 \
  --maxKVCacheCapacity 2048 \
  --maxSpecDraftTokens 60 \
  --specDraft

Run#

# Greedy chain
./build/bin/llm_inference \
  --engineDir "$MODEL_ROOT/engines" \
  --inputFile "$INPUT_FILE" \
  --outputFile "$MODEL_ROOT/output.json" \
  --specDecode \
  --specDraftTopK 1 \
  --specProposalTokens 15 \
  --specVerifyTokens 16

# DDTree verification on the same engines
./build/bin/llm_inference \
  --engineDir "$MODEL_ROOT/engines" \
  --inputFile "$INPUT_FILE" \
  --outputFile "$MODEL_ROOT/output.json" \
  --specDecode \
  --specDraftTopK 4 \
  --specVerifyTokens 60

  • --specProposalTokens 15 --specVerifyTokens 16 with --specDraftTopK 1 verifies the full block-16 chain including the root token

  • --specVerifyTokens up to --maxSpecVerifyTokens (at most 128) sets the tree node budget; --specDraftTopK (at most 8) is the per-depth fanout. On Qwen3-8B, --specDraftTopK 4 --specVerifyTokens 60 adds about 14% acceptance length on GSM8K and 30% on MT-Bench over the chain

  • Jump-forward needs nothing extra on the chain. DDTree verification needs --specVerifyTokens below --maxSpecVerifyTokens; the tree command above verifies all 60 positions and does not jump

Quantization#

The base and the draft are quantized independently and any FP8, NVFP4, or INT4-AWQ combination builds with the commands above. Quantize the base with trtedge quantize llm (add --kv_cache_quantization fp8 for an FP8 KV cache) and point the base export at the quantized checkpoint. The public Domino drafts ship in BF16; create a quantized draft with trtedge quantize draft, then pass its output directory as --domino-draft-dir to both exports:

trtedge quantize draft \
  --base_model_dir "$MODEL_DIR" \
  --draft_model_dir "$DRAFT_DIR" \
  --output_dir "$MODEL_ROOT/checkpoints/draft-nvfp4" \
  --quantization nvfp4

Precision is detected from the checkpoint quantization metadata. The target-hidden projector, the candidate-pool projection, and the GRU correction head stay FP16 in every draft precision; only the draft transformer layers are quantized.

ONNX-less Alternative#

The experimental trtedge build frontend reads local checkpoints and builds the base and draft engines in one command. It does not export or parse ONNX. Complete the direct-builder prerequisites before using this path.

For embedded Qwen3.5 MTP:

trtedge build \
  --model-dir "$WORKSPACE_DIR/Qwen3.5-4B-mtp/checkpoints/base" \
  --engine-dir "$WORKSPACE_DIR/Qwen3.5-4B-mtp/direct-engines" \
  --spec-type mtp \
  --max-input-len 2048 \
  --max-kv-cache-capacity 4096 \
  --max-batch-size 1 \
  --max-spec-verify-tokens 4 \
  --max-spec-draft-tokens 4

Paired methods add --draft-model-dir and select their method:

# EAGLE3
trtedge build \
  --model-dir "$WORKSPACE_DIR/Qwen3-1.7B-eagle3/checkpoints/base" \
  --draft-model-dir "$WORKSPACE_DIR/Qwen3-1.7B-eagle3/checkpoints/draft" \
  --engine-dir "$WORKSPACE_DIR/Qwen3-1.7B-eagle3/direct-engines" \
  --spec-type eagle3 \
  --max-input-len 1024 \
  --max-kv-cache-capacity 2048 \
  --max-batch-size 1 \
  --max-spec-verify-tokens 60 \
  --max-spec-draft-tokens 60

For DFlash, LiLiCorr, Domino, or DSpark, use that section’s checkpoint paths, tree sizes, and --spec-type. Direct-built DSpark and Domino support both chain mode and greedy tree mode using the same target artifact; --spec-type domino also writes domino_heads.safetensors next to the draft engine. Run direct-built engines with the same method-specific inference settings shown above. Change --engine-dir to the direct engine directory and add --checkpoint-dir <base_checkpoint>. Paired methods also require --draft-checkpoint-dir <draft_checkpoint>.
