GR00T N1.7#

GR00T N1.7 is NVIDIA Isaac’s flow-matching Vision-Language-Action model. Edge-LLM runs it as three TensorRT components driven by an experimental C++ policy runtime: camera views, an instruction and a robot state in, an action chunk in robot units out. See the GR00T N1.7 example for the build, run and verify walkthrough; this page records the contracts.

Two build routes write the same bundle. The ONNX-less direct builder (tensorrt_edgellm/builder/models/gr00t_n1d7) compiles the checkpoint on the target; tensorrt-edgellm-export (tensorrt_edgellm/models/gr00t_n1d7) writes ONNX on CPU and gr00t_policy_build compiles it. The checkpoint facts, request geometry, component contracts and constant-table math are one implementation under tensorrt_edgellm/models/gr00t_n1d7, imported by both, so the runtime reads one config.json shape and one policy.json whichever route produced them. The ONNX route lowers attention to trt::attention_onnx / trt::rope_onnx, the path pi0.5’s prefix takes; the cross-attention masks stay bool engine inputs and become additive fp16 inside the graph.

Checkpoint#

nvidia/GR00T-N1.7-LIBERO, the libero_10/ subdirectory. The checkpoint carries model_type: Gr00t and nests everything under two roots: the backbone under backbone.model.model. and the policy head under action_head.. It ships no tokenizer; upstream loads the backbone’s (Qwen/Qwen3-VL-2B-Instruct, byte-identical to Cosmos-Reason2-2B’s) from the Hub, and the builders expect the same files under tokenizer/ in the checkpoint directory.

Its Cosmos-Reason2-2B backbone config lives in a separate, gated repository, so the backbone geometry is declared in tensorrt_edgellm/models/gr00t_n1d7/configuration.py and checked against the checkpoint’s own tensor shapes. A checkpoint that is not this architecture fails before a network is created rather than building a silently wrong engine. Cosmos-Reason2-2B is post-trained from Qwen3-VL-2B-Instruct and keeps its architecture, so the vision tower is the shared Qwen3-VL encoder and needs no new modeling code.

The released checkpoint already carries only select_layer (16) of the backbone’s 28 text layers; the reference pops the rest at load time.

Two invariants the graph relies on and cannot check:

  1. DeepStack inputs are zero outside image-token positions. Qwen3-VL scatter-adds its DeepStack features at image tokens; the graph adds the whole tensor, which is the same thing only if the caller zero-fills the rest. This matches the shared DecoderModel contract.

The 32 DiT blocks alternate: odd blocks self-attend over the 41 state+action tokens, even blocks cross-attend into the VL context. attend_text_every_n_blocks is 2, so a cross block reads the text mask when idx % 4 == 0 and the image mask otherwise. Build-time constants#

num_inference_timesteps is fixed by the checkpoint, so everything that depends only on the timestep is evaluated by the builder and bound per step instead of being rebuilt by the action graph.

the timestep half of the action encoder’s W2, plus the concatenation

Row i is block i’s norm1.linear output and the last row is proj_out_1. The two split their output in opposite orders — (scale, shift) for the blocks, (shift, scale) for proj_out_1 — so the raw projection is stored and the graph owns the split.

The embodiment id is also fixed at build time, so CategorySpecificLinear’s W [32, in, out] gather is resolved in the builder. It is read from the checkpoint’s embodiment_id.json by matching its tags against the checkpoint directory name, which selects libero_sim (id 2) for libero_10; --gr00t-embodiment-id overrides it and an unmatched directory falls back to unknown with a warning. That drops 31/32 of the weights on the state encoder, action encoder and action decoder; the action encoder alone goes from ~466 MB stacked to ~15 MB, and it runs every denoise step.

An embodiment is a slot inside the checkpoint rather than a checkpoint of its own: the backbone is shared and only those three modules carry per-embodiment rows. libero_10 names 52 tags over 17 ids, of which 9 carry both statistics and a modality config; eight of those nine declare rep: RELATIVE, type: EEF actions, so libero_sim is the only one whose action representation this runtime implements. An engine bundle is therefore built for one embodiment, and another needs another build.

Policy contract#

The builder resolves the embodiment’s statistics and joint-group order into action/policy.json, so the runtime needs two flat vectors and one slice width instead of the checkpoint’s nested processor config.

field

LIBERO value

embodiment_tag / embodiment_id

libero_sim / 2

state.keys / dims

x y z roll pitch yaw gripper / 1 1 1 1 1 1 2 (8 wide, padded to 132)

action.keys / dims

same keys / all 1 (7 wide)

action.horizon

16 – len(delta_indices), shorter than the model’s 40

bounds

q01 / q99, since use_percentiles is true

export_id / frontend / checkpoint_fingerprint

the build’s identity, also stamped on every component config.json

export_id hashes the checkpoint’s weight fingerprint with the options that change the engines (embodiment id, context and image lengths, route), so rebuilding one component from the same inputs reproduces it. Both builders refuse to write beside a component carrying another id, and the runtime refuses a bundle whose components disagree on id or route, or carry none. They also refuse a checkpoint without tokenizer/, its tokenizer.json and a chat template before any engine is written, since the runtime loads all three.

Gr00tPolicy applies the reference’s own formulas: normalization is 2 * (x - q01) / (q99 - q01) - 1 clipped to [-1, 1], with a degenerate joint group mapping to zero rather than dividing by its range; unnormalization is (clip(x, -1, 1) + 1) / 2 * (q99 - q01) + q01 and has no such guard.

Only absolute action representations are supported. The builder rejects a checkpoint whose action_configs ask for relative-to-absolute conversion, which would need end-effector pose math the runtime does not implement. LIBERO is absolute throughout.

Precision#

FP16 only. The graphs are built from a bf16 checkpoint with no quantization metadata, so Net.linear_from_weights takes its FP16 path throughout.

Measured on Thor SM110, FP16, batch 1, 4 denoise steps, against a float32 PyTorch reference assembled from Isaac-GR00T’s own dit.py and HuggingFace Qwen3VLForConditionalGeneration. The policy head is driven with identical embeddings, DeepStack features, rotary tables, masks, state and initial noise; the vision front end is scored on two LIBERO views and a task instruction, against the same checkpoint’s tower behind HuggingFace’s Qwen3-VL processor.
